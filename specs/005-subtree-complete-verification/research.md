# Phase 0 Research: Subtree-Complete Heal Verification

Grounded in a `forge` impact analysis of the current `staging` tree (consensus-adjacent — this changes the completeness *proof*). File:line citations from `staging` HEAD.

## Current-state findings (why the ~20h re-walk exists)

- **F-A — Discovery and verification are the same code, run for different reasons.** Both `discoverMissingChildren` (incremental, `:1917`) and `rebuildFrontierBFS` (the verification BFS, `:1529`) emit missing nodes via `FrontierRebuilt`. The discovery walk's "stop at a present node" is **unsound** — it *assumes* present-parent ⇒ complete-subtree (RUN10: account `888157b2` had 11 missing storage nodes after StateHeal declared complete; `:1868-1871`). The full verification BFS re-derives the frontier from **on-disk reality** (`multiGetNodes(chunk)`, `:1598`), independent of the in-memory `pendingTasks` frontier, pivot-roll clears (`:232/:241`), and the bounded `visitedLru` (`:1549`).
- **F-B — Single completion chokepoint.** `HealingCheckCompletion` (`:889-912`): completion declared only if `verificationPassComplete || totalNodesHealed==0`; `verificationPassComplete` set at exactly one site (`:953`, in `VerificationBFSComplete`); `markComplete()` written at one site gated on it (`:906-911`); `StateHealingComplete` sent at one site (`:912`). `isComplete` (`:1495`) = `pendingTasks.isEmpty && activeRequests.isEmpty` (necessary, not sufficient).
- **F-C — The marker is only set after a full walk.** Spec-003 scoped verification (`:923-931`) engages only when `healingFrontierStorage.exists(_.isComplete)` (`:925`) — a marker set only *after* a prior full walk. On a fresh node the marker is never set ⇒ the **first** verification is always full-trie (`startVerificationBFS` `:1873`). That is the ~16-20h cost spec 005 targets (FR-003).
- **F-D — "present parent ⇒ complete subtree" does NOT hold today.** The heal write path is **top-down** (root seeded first `:623`, children discovered from the decoded parent `:1333`), so a present branch routinely sits above not-yet-fetched children. Plus: range boundaries between 16 independent StackTrie fragments (`AccountRangeCoordinator` `:1488/:1573-1589` — "no single computed root… healing reconciles"), incomplete-storage accounts (RUN10), and pivot-delta. Descend-and-stop is therefore **unsound today** without a new durable invariant.
- **F-E — The walk performs NO state writes.** `rebuildFrontierBFS` is a pure local read (`:1526-1527`); the state root is whatever SNAP+heal already put on disk. So byte-parity reduces entirely to "emit the same set of missing nodes."
- **F-F — Existing substrate to reuse.** `HealingFrontierStorage` (CF `'g'`, `Namespaces.scala:20`) already persists the frontier + a completeness marker (`markComplete`/`isComplete`, `:50-69`) and safely holds a non-32-byte sentinel key (the 21-byte `CompleteMarkerKey`, `:64-69`). The spec-004 fetched-node content-hash guardrail (`keccak256(node)==requested hash`, `:1290`) is independent and stays.

## Decisions

### D1 — Mechanism: content-addressed per-subtree-complete records in CF `'g'` (forge's (C)-as-(B)); reject (A)

- **Decision**: Add a durable **per-subtree-complete record** keyed by the node's bare keccak hash with a non-32-byte prefix (e.g. `0x01 ++ hash`, 33 bytes) in the existing `HealingFrontierStorage` CF `'g'`. The verification (`rebuildFrontierBFS`) consults it before descending a present child; if recorded, it prunes (treats the node as a verified leaf). When a subtree closes with zero missing descendants, it records the subtree root.
- **Rationale**: The **key insight — subtree-completeness is ROOT-INDEPENDENT.** Nodes are content-addressed, so a node's children are fixed by its content; once hash X's entire subtree is proven present, that fact is *eternal* and valid across pivot rolls — so the record needs **no invalidation/clearing** (unlike the global marker cleared at `:241`). Records are additive + monotone (healing never deletes present nodes). Reuses CF `'g'`, no new column family, no migration. Absent record ⇒ descend ⇒ today's behavior (safe fallback).
- **Rejected — (A) bottom-up write ordering** (present-parent always ⇒ complete-subtree): incompatible with the inherently **top-down** heal path (`:623/:1333`); would require unbounded in-memory subtree buffering on a 90M-node trie; cannot retrofit already-synced on-disk state; and `setSync(false)` (`RocksDbDataSource.scala:122`) means write-order ≠ durability-order without per-subtree fsync barriers.
- **Rejected — fine-grained always-on 90M-entry index**: heavy; the coarse on-demand record (only for subtrees actually proven) is sufficient.

### D2 — Seed the invariant across the SNAP→heal boundary so the FIRST verification is O(missing) (FR-003)

- **Decision**: Record subtree-complete (a) for each StackTrie fragment root when `SnapHashTrie.commit()` durably lands (each fragment is internally bottom-up-complete; `AccountRangeCoordinator` finalize `:1573-1594`), and (b) for each heal subtree as `discoverMissingChildren` confirms a node has zero still-missing children (`:1949` region). This pre-populates the records so the first verification descends only the inter-fragment boundaries + residual gaps → O(missing).
- **Rationale**: FR-003 requires the invariant to hold on a fresh node's *first* verification. Recording only *during* the first verification would leave that first walk full (~20h) — defeating the feature. Seeding at write time is what makes the first verification cheap.
- **Guard (forge)**: never seed from an **abandoned** StackTrie fragment (`SnapHashTrie.reset()` on pivot roll, `:80`) — record only for a successfully-committed fragment whose every emitted node landed. Never record based on a **truncated** (LRU-evicted) descent — records must derive from genuine zero-missing closure, not "queue drained."

- **CORRECTION (2026-06-19, forge adversarial review — BLOCKER fixed before merge): the SNAP account-fragment seed (a) is UNSOUND and was DROPPED.** An account-trie fragment root's subtree includes the storage tries referenced by its account leaves' `storageRoot`. SNAP downloads all accounts *before* any storage, so at account-fragment commit those storage tries are not yet present; recording the fragment root subtree-complete (a content-addressed, never-cleared record that later matches a real pivot-trie node) would let the verification prune it and miss a still-absent storage node → false `StateHealingComplete` → state-root mismatch (FR-002 violation). **Seeding is now ONLY (b) the heal-side inductive closure** in `discoverMissingChildren` — which records a node solely when every present child *including the account leaf's `storageRoot`* is itself recorded subtree-complete — **plus the genuine zero-missing root record at the completion chokepoint.** These never produce an unsound record. FR-003 (first verification O(missing)) is delivered by the heal-side seeding; seeding sound *storage*-fragment roots (option B) is a deferred follow-up if the heal-side seeding proves insufficient. The `AccountRangeCoordinator` seeding code + its threading were removed entirely.

### D3 — Crash-safety ordering (FR-006): record-after-persist; terminal marker fsynced

- **Decision**: Write a subtree-complete record for X **only after** X's subtree bytes are in a committed `WriteBatch` (mirror `unpersistFrontier`'s post-`persist` rule, `:489-490/:510-511`). Ordering: children node-bytes (CF `'n'`) committed → then parent subtree-complete record (CF `'g'`) via ordinary `update` (WAL-ordered) → then, only at the very end, the global `markComplete()` via `updateSync` (fsync, `RocksDbDataSource.scala:128`).
- **Rationale**: A crash between stages leaves the record absent ⇒ restart **descends** (safe, FR-006). The dangerous order (record before children durable) is structurally forbidden. Per-subtree records can be cheap WAL-ordered `update` (loss ⇒ safe descend); the terminal proof gets fsync durability (mirrors the existing SNAP-finalization fsync rationale, `:124-127`).

### D4 — Byte-parity via the single chokepoint (FR-005)

- **Decision**: The pruned walk remains `rebuildFrontierBFS` emitting `FrontierRebuilt` for any missing node and `VerificationBFSComplete` when done — routing through the *same* `verificationPassComplete` → `HealingCheckCompletion` → `markComplete`/`StateHealingComplete` chokepoint (F-B). Pruning changes only *which present nodes are read*, never which missing nodes are emitted, never the terminal messages.
- **Rationale**: Given the invariant holds (D1/D3), the pruned walk emits **exactly the same set of missing nodes** as the full walk (zero, for completion) ⇒ identical `isComplete` ⇒ identical marker bytes (constant `Array[Byte](1)`) ⇒ identical `StateHealingComplete` ⇒ identical state root (the walk does no state writes, F-E). Byte-parity reduces entirely to the never-false-prune invariant.

### D5 — Hash scheme only; Path scheme + no-records ⇒ full-walk fallback (FR-007)

- **Decision**: Gate the pruned verification on `storageScheme == Hash` (the ETC default) AND a config flag. Under StorageScheme.Path (nodes keyed by nibble-path, `:1291/1294`), the hash-keyed record doesn't apply ⇒ fall back to the existing full walk. Flag off OR no records present ⇒ full walk (`startVerificationBFS` `:1873`, unchanged).
- **Rationale**: The record keys on the bare keccak hash (independent of ref-counting / `StoredNode` serialization — it lives in CF `'g'`, not the ref-counted node CF `'n'`); this is well-defined only under Hash addressing. Safe-to-flip-without-migration: absent record ⇒ descend.

### D6 — Config switch `pruned-heal-verification`, default on, full-walk fallback

- **Decision**: Add `sync.snap-sync.pruned-heal-verification` (boolean, default **true**, mirroring `scoped-heal-verification`/`heal-hold-pivot-on-stagnation`/`decoupled-heal-serve-root`). Thread through `SnapSyncConfig` + `props` + `SNAPSyncController`. Off ⇒ existing full-trie verification, byte-identical.
- **Rationale**: In-memory/additive records only; safe to flip without migration. Default-on to deliver the value; the FR-007 fallback keeps it correct.

## Consensus-safety conclusion (forge)

**The load-bearing risk:** any path where a present node is pruned without its subtree being *durably proven complete* ⇒ a missing descendant goes undetected ⇒ false `StateHealingComplete` ⇒ state-root mismatch at block execution ⇒ wedged/forked node. Guarded by: record-after-`persist` ordering (D3); descend-on-missing-record fallback (D1/D5); never seed from abandoned StackTrie fragments or truncated descents (D2). The spec-004 fetched-node content-hash guardrail (`:1290`) is preserved unchanged (FR-008) — this feature changes how *present* nodes are verified for subtree presence, not how *fetched* nodes are trusted for content. No EVM/gas/RLP/Ethash/ECIP-1017 code is touched; the verification is a pure local read that never recomputes or mutates the state root.
